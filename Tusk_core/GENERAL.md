# GENERAL: コーディング・テスト・リカバリー共通方針

## 1. Tusk Core 境界と単一正本原則

- Coreはドメイン非依存とする。製品固有規則、ソース、履歴をCoreへ混ぜない。
- 1つの規範的概念には正本を1つだけ持つ（`AUTHORITY-MAP.json` 参照）。
- 制作中の会話へ思考履歴や長いログを出力しない。根拠はログ、差分、JSON、仕様書へ保存し、返答は最低限の結果・判定・次の行動だけとする。
- コード内コメントは原則として追加しない（必要なヘッダ規約を除く）。

## 2. 実装強度（Intensity）と危険度（Process Level）

作業開始時に対象仕様、キャッシュ、対象差分から、技術的難易度 `implementation_intensity`（`LOW` / `MID` / `HIGH` / `MAX`）と安全工程 `process_level`（`P0`〜`P4`、`PROCESS_POLICY.md` 参照）を独立に決める。

- 通常の `LOW`、`MID`、`HIGH` 作業は途中承認を要求せず、ユーザーの作業指示を開始許可として実装、監視テスト、上限内の限定修正まで進める。
- 人間の明示承認が必要なのは、`MAX`、破壊操作、workspace外変更、配布・Installer、認証・秘密情報、利用者データ、または限定ロールバック（`rollback`）実行時とする。

## 3. 作業中変更のリカバリーと再作業上限

既存の「停止したら作業中変更が宙に浮く」問題を解決するため、軽量セッション記録（`work/recovery/sessions.jsonl`）と対象ファイル退避（`work/recovery/backups/<work_id>/`）によって作業中の変更を安全にリカバリーする。

### 再作業上限と停止規則
- `MAX_REWORK_COUNT = 3` とする（初回実装と初回テストは数えない）。
- 同一の失敗（`error_key + 対象ファイル + 失敗工程`）が2回連続した時点、または上限3回に達した時点で後続を止め、`work/focus_cache/LANDMINES.md` へ地雷を記録して `waiting_human`（または `needs_human_review`）へ停止する。
- テスト本体実行前のコマンドパス・引用符・起動形式だけの不備は `preflight_error` とし、対象コードを変更せず1回だけ機械的に経路補正して再実行できる。

### 作業状態（6状態）
- `running`: 仕様と許可範囲内で自動処理を継続中。
- `needs_review`: 技術情報または根拠不足により読み取り専用確認待ち。
- `waiting_human`: 途中停止、非ゼロ終了、外部変更検出などにより人間の指示待ち。作業中差分は保持される。
- `needs_human_review`: 再作業上限到達、承認範囲超過など人間の再判定が必須。
- `completed`: 全成功条件、成果物検証、必須テストを通過。
- `abandoned`: 未完了のまま終了し、引き継ぎ証拠を保存した状態。

### 作業中変更のリカバリー操作（4アクション）
`waiting_human` で停止した作業中の変更に対し、`tusk_manager.py session` で以下の4操作を行える：

1. **`resume`（そのまま再開）**:
   - 停止時点の作業中変更（WIPスナップショット）と対象ファイルSHAが一致していることを確認し、`rework_count` を維持したまま続きから再開する。
2. **`revise`（方針・スコープ改訂再開）**:
   - 作業中の変更を活かしつつ、人間が修正方針や対象 `scope` を更新して新世代（`generation + 1`）として再開する。作業中に新規追加したファイルもそのまま引き継げる。
3. **`rollback`（作業開始前・直前チェックポイントへ限定復元）**:
   - **既存の無関係なユーザー変更やログ・キャッシュを一切壊さず**、今回の `work_id` が対象 `scope` に対して行った変更だけを開始時（または指定世代）のバックアップから正確に復元し、作業中に新規作成したファイルだけを安全に除去する。
4. **`abandon`（破棄・引継ぎ保存）**:
   - 作業中の差分と失敗証拠を保持したまま未完了終了とし、次世代タスクへの地雷（Focus Cache）を残す。

## 4. コード生成・保護規則

1. 指定された `scope`（変更可能パス）外のファイル、ID、件数、順序、原文を変更しない。
2. 既存ログ、入力、失敗成果物を削除・上書きしない。
3. 同一ワークツリーの同一ファイルを複数エージェントが同時編集しない。並列化は対象・境界・競合防止策を提示し、人間承認後だけ行う。
4. 例外を握りつぶさない。継続不能なら強制停止（`Fxxx`）、継続可能なら軽度問題（`Mxxx`）へ分類する。
5. 自動再起動、無制限再試行、成功条件の緩和を実装しない。
6. リポジトリ全体への `git reset --hard` は禁止する。復元は必ず `tusk_manager.py session rollback` による対象scope限定復元を使う。

## 5. 完了条件

- 個別仕様の全成功条件と必須テスト（`TEST_POLICY.md`）を満たす。
- 最新実行の件数、ID集合、更新時刻、SHA-256、成果物を確認する。
- 強制停止（`Fxxx`）が存在せず、対象外ファイルの意図しない変更がない。
