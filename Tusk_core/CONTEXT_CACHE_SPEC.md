# コンテキストキャッシュ共通仕様

## 1. 目的

大規模な制作物を毎回全文走査せず、現在の構成、差分、関連仕様、ログ索引へ限定して到達するための計画単位キャッシュを定義する。キャッシュは原本の索引であり、仕様、テスト結果、成果物、完成判定の代替にしない。

## 2. 分割単位

- 一つのワークスペースを単一キャッシュへ集約しない。
- 独立して開発、レビュー、検証、引継ぎできる程度の主要領域ごとに`scope_key`を割り当て、キャッシュファイルを分ける。
- 主要領域は製品フェーズ、アプリ、サービス、サブシステム等とする。フォルダ数やファイル数だけで機械的に分割しない。
- 二つの領域を同時入力する必要がある場合も、それぞれのキャッシュを維持し、共通キャッシュへ内容を複製しない。
- 複数領域で共有するのはワークスペース構成、scope一覧、run索引等の最小メタデータだけとする。

## 3. 標準配置

```text
<workspace>/work/context_cache/
├─ common/
│  ├─ workspace_manifest.json
│  └─ log_index.jsonl
├─ <scope_key>/
│  ├─ context_manifest.json
│  ├─ log_state.json
│  ├─ current_state.md
│  ├─ session_handoff.md
│  └─ test_matrix.json
└─ <next_scope_key>/
   └─ ...
```

現行フェーズで実装されていない補助ファイルは空で作らない。`context_manifest.json`、`workspace_manifest.json`を基礎とし、増分ログ要約を使う領域だけ`log_state.json`と共通`log_index.jsonl`を使う。

## 4. プロジェクトバインド

各プロジェクトは次をローカル仕様へ固定する。

- `scope_key`一覧と各ソースルート
- 共通規則、対象仕様、入口、ログの場所
- 除外パスと読み取り専用領域
- キャッシュ生成、差分読込、ログ要約のコマンド
- 実装済みフェーズと未実装ファイル
- scopeを跨いで参照できる公開契約

バインドにないscope、ルート、物理パスマッピングを推測しない。不明な場合は`needs_review`とする。

## 5. Manifest契約

`context_manifest.json`は原本への索引として、少なくとも次を保持する。

- 正規化済み相対パス
- SHA-256、サイズ、更新日時
- `rule`、`spec`、`code`、`test`、`state`等の種別
- 追加、変更、削除の差分状態
- 直接参照する仕様または入口
- 取得失敗と`needs_review`

`workspace_manifest.json`はworkspaceとscopeの対応だけを保持し、各scopeのファイル索引を複製しない。キャッシュは再生成可能とし、生成処理だけが原子的に更新する。

## 6. 読込手順

1. workspaceと対象scopeを一つ確定する。
2. 適用される`AGENTS.md`と対象scopeのバインドを読む。
3. 生成を伴わないdry-runで件数、差分、除外、エラーを確認する。
4. 対象が正しい場合だけmanifestを更新する。
5. 追加・変更ファイルと直接参照仕様だけを限定読込する。
6. ログは増分索引を先に読み、証拠不足または`needs_review`の場合だけ生ログの該当範囲を読む。

別scope、未変更ファイル、archive、依存物、ランタイム、バイナリ本文、過去ログ全文を既定入力にしない。

## 7. ログ索引

ログ索引は一実行一行を基本とし、run ID、scope、仕様、時刻、入口、終了コード、状態、最初の失敗、件数、ID集合ハッシュ、成果物SHA、原本ログパスを保持する。

- 読込済みbyte offsetはscope別`log_state.json`へ保存する。
- 共通`log_index.jsonl`はscopeとrun IDで検索する。
- 初回の部分読込、ログ欠損、状態不明を成功へ確定しない。
- 正常時は全文をモデル入力へ渡さない。

## 8. 無効化

次の場合は該当scopeを無効化して原本を再確認する。

- 適用`AGENTS.md`、対象仕様、入口、依存関係の変更
- 記録SHA、サイズ、更新日時と原本の不一致
- scopeルート、名称、物理パスマッピングの変更
- ログ欠損、hash失敗、manifest破損

全scope再構築は共通規則、workspaceルート、scope構成が変わった場合だけ行う。

## 9. フォーカスキャッシュとの境界

- 新規制作、再開、全体整合性確認にはコンテキストキャッシュを使う。
- 既知エラー、誤読、失敗箇所の限定修正にはフォーカスキャッシュを使う。
- コンテキストキャッシュへ生の推論、修正命令、頻発エラー教材を保存しない。
- フォーカスキャッシュへworkspace全体のmanifestやログ索引を複製しない。

## 10. 安全条件

- キャッシュ生成はソース、仕様、生ログ、成果物を変更しない。
- キャッシュ命中だけでテストを省略、成功、完成と判定しない。
- 未承認、未完了、失敗中のデータを有効知識として扱わない。
- 生成前にdry-runし、非ゼロ終了またはエラー時は実生成しない。
- 失敗後に実機処理を自動再起動しない。

## 11. 成功条件

- scope指定時に他scopeを既定で読まない。
- 未変更ファイルと生ログ全文を再読込しない。
- SHA不一致と欠損を`needs_review`へ移す。
- 共通キャッシュへscope固有本文を重複保存しない。
- キャッシュが無効でも原本確認へ安全にフォールバックできる。
