# GENERAL: 共通作業規則

## 目的

この文書はTusk Coreを利用する全作業へ常時適用する、ドメイン非依存の作業規則を定義する。製品仕様、実装経路、安全工程、テスト方式、エラー体系、権限、整合性、Cacheの詳細はそれぞれの正本を参照し、ここでは再定義しない。

Coreは製品、Adapter、旧プロジェクトの契約を所有しない。製品固有の語彙、マーカー、閾値、操作手順、実行コマンド、履歴は有効化されたExtensionまたは現行Specへ置く。

## 規則の優先順位

1. 明示されたユーザー要求と対象の現行Specを確認する。
2. workspaceとCoreの`AGENTS.md`に従い、有効化とmanifest検証を通ったExtensionだけを選ぶ。
3. `AUTHORITY-MAP.json`が指定する概念ごとの正本を読む。
4. Extensionの規則はその製品領域だけに適用し、Coreの共通契約を製品固有規則で上書きしない。
5. 入力が不足、矛盾、未検証の場合は推測せず`needs_review`とする。

一つの規範的概念には正本を一つだけ持つ。他文書は意味、表、状態、番号、閾値を再定義せず、正本を参照する。機械判定可能なregistry、対応表、schema、分類処理はMarkdownへ複製しない。新規Authorityは既存正本で扱えない独立概念に限り、Creation Gateを通して追加する。

## 全作業共通原則

1. 作業対象は、選択済みExtension、現在の要求、現行Spec、Git差分、検証済みContext Cacheから導出する。独立したScope文書を入力にしない。
2. 作業開始前に対象、変更可能パス、変更禁止パス、成功条件、必要な検証を確定する。
3. 指定外ファイル、無関係なユーザー変更、別担当の差分を変更、削除、復元しない。
4. 読み取り可能範囲と変更可能範囲を分ける。追加の参照や変更が必要なら、範囲を更新してから進む。
5. 同一ファイルへ複数writerを置かない。並列化は独立した対象、担当境界、依存関係、競合防止策が確定した場合だけ行う。
6. 既存構造を優先し、必要な最小差分で変更する。理由のない全面書換え、別方式への置換、仕様外の改善を混ぜない。
7. 変数、ID、件数、順序、原文、互換契約を推測で変更しない。新しい値が必要なら現行Specへ明示する。
8. 既存ログ、入力、失敗成果物、検証証拠を削除または上書きしない。新しい実行は識別可能な単位へ分離する。
9. 例外を握りつぶさない。継続不能な失敗と継続可能な問題を正本のエラー規則へ従って区別する。
10. 自動再起動、無制限再試行、条件緩和、失敗の名称変更による別件化を行わない。
11. 実装担当は指定範囲の実装と静的確認を行い、テスト成功、状態解除、完成を自己承認しない。
12. コードレビューを通った差分だけを実行テストへ渡す。テスト中に製品コード、テストコード、fixture、期待値を変更しない。
13. テストは現在差分と現行Specから選ぶ。下位テストの成功で必要な上位テストを省略しない。
14. 終了コード、ファイル生成、ログ生成だけで成功と判定しない。期待した差分、件数、成果物、必須検証を確認する。
15. 失敗時は後続工程を止め、証拠を保持して正本の停止・再作業規則へ渡す。停止状態を担当者や監視処理が独自に解除しない。
16. 破壊操作、workspace外変更、配布、認証、秘密情報、利用者データなど、正本が明示承認を要求する操作は承認前に実行しない。
17. 秘密情報、生の思考履歴、不要な長大ログを成果物、Cache、会話へ保存しない。判断根拠は検証可能な差分、ログ、構造化データへ残す。
18. 完了は現行Specの成功条件、必須テスト、成果物検証、未解決事項、最終レビューを確認してから宣言する。
19. リポジトリ全体または既存のユーザー差分へ作用する`git reset --hard`、一括checkout、同等の破壊的復元を行わない。rollbackは`PROCESS_POLICY.md`の分離・承認条件へ従う。
20. コードコメントは原則として追加しない。実装理由、外部制約、安全条件をコードだけで明確に表現できない場合に限り、短い検証可能なコメントを残す。

## Authority参照

| 確認する概念 | 正本 |
|---|---|
| 技術難度、実装経路、Provider、MAX | `ROUTING_POLICY.md` |
| Process Level、安全工程、停止、再作業、再開 | `PROCESS_POLICY.md` |
| テスト選択、stage、監視、証拠、完了検証 | `TEST_POLICY.md` / `TEST-MAP.json` |
| エラー文法と共通コード | `ERROR_POLICY.md` / `ERROR_CODES.md` |
| 実行権限、提案権限、担当境界 | `AUTHORITY_SEPARATION.md` |
| 配布物、manifest、開発権限の整合性 | `INTEGRITY_POLICY.md` |
| Context Cache | `CONTEXT_CACHE_SPEC.md` |
| Focus Cache | `FOCUS_CACHE_SPEC.md` |
| 同期と競合停止 | `SYNC_POLICY.md` |

正本間に矛盾がある場合は都合のよい規則を選ばない。対象を止め、矛盾する正本、適用範囲、差分、必要な判断を`needs_review`として提示する。

## 作業結果

作業結果には最低限、変更ファイル、実施内容、検証結果、未解決事項を含める。完了を報告する場合は、現行Specの成功条件と必須検証を満たした根拠を示す。失敗または停止の場合は、現在差分、最初の失敗、後続を止めた地点、保存した証拠、再開に必要な条件を示す。
